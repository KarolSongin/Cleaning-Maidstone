# Working foundation

One Next.js App Router application. Public routes render on the server; operational routes have independent authenticated layouts and are never publicly cached. Public content uses tag-based caching in Supabase mode; publishing invalidates the page and sitemap. Tiptap, FullCalendar and React Three Fiber load only in the modules that use them.

Supabase is the production system of record. PostgreSQL migrations own permissions, concurrency checks and transactional mutations. Authenticated operations use the user's Supabase session and database RLS; the service key supports validated enquiry intake, authorised account invitations, verified provider callbacks and authenticated integration jobs. Cleaner views project only assigned-work fields. Storage separates public `website-media` from private `call-recordings`.

Without live credentials, `DEMO_MODE=local` uses persistent PGlite PostgreSQL under `.local/`. It installs the same business and transcription-job migrations with synthetic accounts/data. A signed, HttpOnly cookie selects a fixed synthetic role; this mode binds to loopback and is refused on Vercel. It must never be used as production authentication. Schema tests exercise real PostgreSQL policies and mutations, including concurrent overlap constraints.

Recurring visits store a Europe/London wall time plus interval on a series and UTC instants on occurrences. Occurrences are materialised transactionally for a chosen 1–52-week period (52 weekly or 26 fortnightly visits at the maximum). The series stores `duration_weeks` and an inclusive `ends_on` date, separate from individual visit exceptions. The form previews both the period end and last regular visit. Legacy periods are reconstructed from the original visit count, including cancellations, without changing visits. Exclusion constraints prevent simultaneous overlap; database checks also enforce availability and approved leave. Moving/cancelling an occurrence affects only that visit and preserves the contractual period. Renewal flags begin one calendar month before `ends_on`, including month-end clamping, and remain due through the expiry date; the following day is ended. Admins can filter the complete series list, see contact details and add a persistent customer follow-up task. Date-only fields are normalised to YYYY-MM-DD in the embedded demo to match PostgREST. Supabase schedule/series reads use ordered pagination to avoid truncating a year of visits at a per-request row limit; live provider validation remains outstanding.

Booking finances are stored as integer GBP pennies per hour in admin-only `visit_finances` and `series_finances` tables. New bookings require a positive customer rate equal to the nonnegative admin share plus cleaner cash rate (up to £1,000 per hour). API validation, guarded RPCs and table checks enforce the split. The original series rate and each occurrence snapshot are inserted in the booking transaction, so a later conflict rolls everything back. An admin can price an existing visit or explicitly change its snapshot without changing sibling visits or the series agreement; rescheduling preserves rates. Older visits are unpriced rather than assigned fabricated values. Customer and cleaner totals round to pennies using the booked elapsed duration; the admin total is the difference, so totals balance even when a half-penny occurs. These are agreed amounts, not received-payment records. Stripe subscriptions and payment collection remain future work.

Cleaners never read full financial rows, including through direct joins. The security-definer `cleaner_jobs` projection exposes only an assigned job's cleaner cash hourly rate and rounded cash total, with nulls for unpriced visits. Visit rows carry no customer/admin prices, and neither finance table is included in Realtime. Financial changes update only a cleaner refresh timestamp in the existing published cleaner row. Admin-only financial mutations are audited. Ordered pagination also covers the financial tables so a year's bookings are fully priced when rendered.

Admin reporting derives values from the complete RLS-visible visit and finance snapshots, with no new payment table or migration. `/admin/finances/` is covered by both the admin layout and section role guard. Completed visits are earned; non-cancelled future/ongoing visits forecast income until their end instant; ended but uncompleted visits await completion. Cancellations remain in the ledger for reference and are excluded from all income totals and active breakdowns. Missing rates remain null, contribute to coverage/visit/hour counts and are excluded from monetary sums; an agreed zero share is priced. Totals add each visit's rounded amounts, preserving penny allocation across groups, including rescheduled or reassigned occurrences. Date filters include both boundaries using the visit's London start date. Current range, customer and cleaner filters feed all metrics, monthly bars and breakdowns; the ledger has a separate category filter and 25-row pagination. CSV exports all matching ledger rows across pages, with cancelled/unpriced rows marked excluded and user-supplied names protected against spreadsheet formulas. An explicit as-of instant keeps server/client status classification consistent; Refresh and successful rate saves update data and time. The financial page shows visit value rather than payment receipts, cash confirmations, overheads, net profit or Stripe subscription status.

Weekly availability is administered at invitation and through a guarded transaction. The cleaner row is locked by both booking validation and hour changes; rejected edits roll back their deleted/inserted periods. Touching periods are merged, and upcoming scheduled or started visits must fit the resulting hours. Existing profiles keep their hours when the additive migration runs. Availability mutations are audited and update a cleaner timestamp, allowing own-row Realtime updates to refresh the read-only cleaner summary without subscribing to deleted availability rows.

The admin calendar projects each selected active cleaner's weekly hours onto London calendar days, subtracts non-cancelled visits and inclusive approved leave, then counts distinct free cleaners across the remaining intervals. Constant-offset day segments handle missing/repeated clock-change hours. Deeper transparent green represents higher simultaneous free capacity. Day/Week shows precise intervals; Month shows the maximum concurrent count per day. A textual slot list provides times, counts and cleaner names alongside the shading.

Phone callbacks use a provider adapter and immutable event keys. The Twilio adapter verifies signatures against the configured public URL. Original and forwarded legs share a root call SID. Recording and transcript stages are independent. Durable database jobs use leases and bounded retries; authenticated provider callbacks fetch completed results. An external scheduler triggers dispatch and retention, with no serverless fire-and-forget work. Recording and transcription start disabled. PWMS reuse remains pending repository details.

Deployment target: Vercel + Supabase. Live site migration, domain changes, user invitations, number purchases, porting and routing activation are separate steps.
